## 1. Fix-me: the closing sentence of §"The same vocabulary in the Kotlin twin"

`skills/swift-sourcery-mocks/references/generated-api.md`, at 0.9.0, closes with:

> Both property getters trap with the same sentence as both method forms,
> `<name>GetHandler expected to be set.`

It sits under the table headed "Members with no counterpart there | this side | Kotlin", so "both"
reads as "both platforms". **A Kotlin property read never traps.** Every property requirement there
falls back to `_<prop>`, which always holds a value — the guessable default, or the constructor
parameter — so `MockRenderer.kt` contains no `GetHandler expected to be set.` string at all; the only
trap is `"<fn>Handler expected to be set."` on a function with no guessable default. `kotlin-ksp-mocks`
002 §2.2 states it: 004 §2.4's second diagnostic has no Kotlin counterpart, because nothing there
corresponds to `/// sourcery: handler`.

Two ways to make it true, whichever reads better here:

- Say which side it is about: "A property getter here traps with the same sentence a method does —
  `<var>GetHandler expected to be set.` — where `/// sourcery: handler` leaves it no store."
- Or move it into the no-counterpart table as a row: `| `<var>GetHandler expected to be set.` from a
  `handler`-annotated property | none — a Kotlin property read falls back to `_<prop>` and never
  traps |`.

The sentence also spells the placeholder `<name>GetHandler` where the rest of the file uses `<var>`.

## 2. The overload tie-break, now measured on both sides

`cf4010e` gave this side its fixture. The Kotlin side has the measurement, taken 2026-09-12 through a
probe consumer on the published processor:

```kotlin
interface Sending {
  fun send(value: String)
  fun send(count: Int)
}
```

emits `send*` for `send(count: Int)` and `sendValue*` for `send(value: String)` — equal parameter
counts are ordered by the joined rendered parameter types, and `kotlin.Int` sorts before
`kotlin.String`.

Two things that follow:

- **`NamingUnlabelledOverload` has no Kotlin counterpart.** `send(_ value: String)` and
  `send(to target: String)` differ only in argument label; Kotlin rejects two functions whose
  parameter types match, so that pair cannot be declared in a shared interface. The labelled/unlabelled
  tie-break is Swift-only, and the two rules cannot disagree about an interface both generators see.
- **Both rules share one hazard**, and neither document states it: within an overload group of equal
  parameter count, adding a member can take the plain prefix from one that already has it — here the
  overload whose first parameter has no label, there the one whose parameter types sort first. The
  guarantee both repositories do state ("adding a wider overload later renames nothing") covers only
  a *wider* one.

## 4. Still open on both sides

D19 here and D6 / §9 there: a method whose handler supplies the publisher returns it before the
`handleEvents` chain on this side, so its subscribe, output and completion counters stay at zero,
while the Kotlin side wraps a handler-supplied `Flow` and counts it. 0.9.0's twin table records the
divergence in a row of its own. Wrapping it here means giving the handler's publisher its own
`Deferred` — `Deferred { self?.<name>SubscribeCount += 1; return handler(args) }` — because Combine
counts the subscription inside that closure.
