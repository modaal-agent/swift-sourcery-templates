## 0. TL;DR

1. A `{ get set }` requirement's setter counts the write and assigns the store (`MockVar.swift:188-193`).
   No member observes a write or records the value written. 004 D12 considered `<var>SetHandler` and did
   not take it (§1.1, §1.2).
2. `proto` counts, appends `newValue` to `<var>SetArgs`, assigns the store, then calls `<var>SetHandler`.
   Over the fast-lane fixtures `Mocks.generated.swift` gains 30 lines and loses none,
   `Components.generated.swift` is unchanged, the six typechecks report 0 diagnostics, the behaviour
   gate passes, and a 12-check behaviour probe passes (§1.3).
3. The consumer repository's 4 settable requirements gain 24 lines: 2803 → 2827 (§1.6).
4. `SKILL.md` reports ~5k on invoke on `master` (212 lines, 14,056 characters). With this change's three
   edits it is 14,174 characters and ~5k, and reports ~4.9k after 250 characters are removed. Cuts of
   facts that references also state bring it to 13,778 characters and ~4.9k (§1.7).
5. `references/generated-api.md` is 249 lines against SC5's 250, and the setter shape adds about 9 lines
   to it (§1.9, §2.4).
6. **Proposed:** the recorder is `<var>SetArgs` (D1); the setter counts, records, stores, then calls the
   handler (D2); a closure-typed property gets the handler and no recorder (D3); `skipArgumentRecording`
   drops `<var>SetArgs` (D4); the naming header lists the new names (D5); `SKILL.md` takes cuts T1 to T3
   (D8). One branch, then the patch release.

### 1.1 What a `{ get set }` requirement generates today

`MockVar.mockImpl` (`templates/Mocks/MockVar.swift:118-221`) has two branches. The smart-default branch
requires a requirement that is not mutable (`:131`), so every `{ get set }` requirement takes the second.

declared is `<var>SetCount` (`:201-203`). `PropertyShaped.draft` in

### 1.2 The method members a setter would follow

- A method appends to `<method>Args` **before** its handler runs (`MockMethod.swift:133-140`), and one
  recorded parameter is stored as `[T]` (`:216-236`). The handler is
  `((_ <name>: <type>, …) -> (<return>))?` (`:247-252`).
- `MethodParameter.isRecordable` excludes a closure parameter (`MockMethod.swift:349-358`): a
  non-escaping closure cannot be stored, and storing an escaping one keeps the caller's captures alive
  as long as the mock. `README.md:117-120` states the same to adopters.
- `skipArgumentRecording` on the method or the protocol turns a method's recording off
  (`MockMethod.swift:208-212`). A property's `recordsStreamValues` reads the same annotation on the
  variable or the protocol, and today governs `<name>Outputs` and `<name>Events` only
  (`MockVar.swift:78-83`).
- The annotation's registry record (`AnnotationRegistry.swift:205-212`) has the effect "Do not generate
  `<method>Args`, `<name>Outputs` or `<name>Events`; counting and the handlers are unaffected", rendered
  into `README.md:813`, `SKILL.md:54` and `references/writing-testable-protocols.md:115`.
- 004 D12 lists the counters that have a handler — `<method>CallCount`, `<var>GetCount`,
  `<method>EventCallCount`, the two token counters — and names `<var>SetCount` as one without. Its option
  (a) added `<var>SetHandler` with three stream handlers, "measured to work … and rejected as speculative:
  no measurement asked for them".

## 2. The shape this proposes

### 2.1 The emission

In `MockVar.mockImpl`'s second branch, for a requirement with a setter (`MockVar.swift:184`). As `proto`
emits it:

```swift
var draft: String {
    get {
        draftGetCount += 1
        if let handler = draftGetHandler {
            return handler()
        }
        return _draft
    }
    set {
        draftSetCount += 1
        draftSetArgs.append(newValue)
        _draft = newValue
        if let handler = draftSetHandler {
            handler(newValue)
        }
    }
}
var draftGetCount: Int = 0
var draftGetHandler: (() -> String)? = nil
var draftSetCount: Int = 0
var draftSetArgs: [String] = []
var draftSetHandler: ((_ newValue: String) -> ())? = nil
var _draft: String = ""
```

1. **The order in the setter** is D2's.
2. **The recorder**, named by D1, is `[<declared type>]` and is appended on every write, whether or not
   the handler is set. Seeding `_<var>` and the generated initializer assign the store and record nothing
   (§1.3).
3. **The handler** is `((_ newValue: <declared type>) -> ())?`, a method handler's form (§1.2). A
   non-optional function type takes `@escaping` in the parameter; an optional one is escaping already
   and cannot carry the attribute (§1.4).
4. **`/// sourcery: handler`** keeps its setter without the store assignment, and gains the recorder and
   the handler (`cursor`, §1.3).
5. **A closure-typed property** follows D3; **`skipArgumentRecording`** follows D4.
6. **Isolation.** Both declarations take `storageIsolationDecl` (`MockVar.swift:47-49`), as `<var>SetCount`
   does: `nonisolated(unsafe)` for a `nonisolated` requirement of an isolated mock (§1.4).
7. **Unchanged:** a `{ get }` requirement, an effectful one, the smart-default branch, the getter, `const`
   and the initializer.

**Superseded in part by §7.3:** item 7 does not hold for a method with a closure parameter, which gains
§7.2's comment, and a closure-typed requirement's `<var>SetHandler` carries the same comment.

## 3. Decisions

### D1 — the recorder's name

- **(a) `<var>SetArgs` (recommended).** A setter is a call taking one value, and a method with one recorded
  parameter records `<method>Args: [T]` (§1.2). A settable property's write members are then `SetCount`,
  `SetArgs`, `SetHandler`, beside a method's `CallCount`, `Args`, `Handler`. `skipArgumentRecording` names
  what it drops, `README.md` §"Recorded arguments" is where the recorders are documented, and
  `kotlin-ksp-mocks` records a call in `<fn>Args` (`generated-api.md:228`). Cost: Swift names the setter's
  input `newValue`, and no property declaration contains the word `Args`, so a reader learns the name from
  the member table.
- **(b) `<var>SetValues`.** Names what it holds. Cost: a fourth recorder word beside `Args`, `Outputs` and
  `Events`, and `skipArgumentRecording`'s name no longer describes one of the members it drops.
- **(c) `<var>SetRecorded`, the request's spelling.** Cost: every recorder suffix in `MockNaming.swift`
  (`:207`, `:235`, `:240`) is a plural noun, `Recorded` is a participle, and `nameSetRecorded` does not name
  what it holds.

**Ruled on 2026-09-15 — §7.1:** (a).

### D2 — the order inside the setter

- **(a) Count, record, store, handler (recommended).** Measured in §1.3. The store holds the new value
  when the handler runs, so a handler that calls back into code which reads the property reads the value
  just written, as it would from a stored property. Cost: the handler cannot read the previous value from
  `_<var>`; the test reads it from `<var>SetArgs`' second-to-last element or from its own capture.
- **(b) Count, record, handler, store.** The handler reads the previous value in `_<var>`. Cost: a read of
  the property from inside the handler returns the previous value.
- **(c) Count, record, then the handler in place of the store assignment when it is set**, as
  `<var>GetHandler` replaces the store read. Cost: while a handler is set, `mock.draft = "a"` followed by a
  read of `mock.draft` returns the earlier value, so setting a handler to observe writes changes what the
  code under test reads.

**Ruled on 2026-09-15 — §7.1:** (a).

### D3 — a closure-typed property

- **(a) The handler and no recorder (recommended).** `<var>SetArgs` is omitted where `TypeName.isClosure`
  is true, the rule `MethodParameter.isRecordable` applies to a parameter (§1.2), which `proto` measured
  true for `(() -> Void)?` and `(Int) -> Int` (§1.4). A non-optional function type takes `@escaping` in the
  handler's parameter.
- **(b) Record it as well.** `[(() -> Void)?]` compiles. Cost: the record keeps each written closure's
  captures alive as long as the mock, which is the reason `README.md:117-120` gives for not recording a
  closure parameter.

**Ruled on 2026-09-15 — §7.1:** (a), with §7.2's comment.
